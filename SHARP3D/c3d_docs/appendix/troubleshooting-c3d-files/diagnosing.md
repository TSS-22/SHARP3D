# Diagnosing C3D Problems

> MLSViewer which were recommended in the original [C3D User Guide](https://www.c3d.org/docs/C3D_User_Guide.pdf) is not available to download anymore. [Mokka](https://biomechanical-toolkit.github.io/mokka/) is discontinued since 13 years, but as you can technically still download and build from source, we kept the parts mentionning it.

As far as we know, at present, your best bet is using [EZC3D](https://github.com/pyomeca/ezc3d), SHARP3D, or any of the main motion capture company software: [Motiv](https://optitrack.com/software/motive), [Nexus](https://www.vicon.com/software/nexus/) or [Qualysis Track Manager](https://www.qualisys.com/software/qualisys-track-manager/). If those applications succeed in opening and displaying the C3D file with problems in other applications then you can examine the file in detail and may be able to determine the cause of the problem by comparing the contents of the problem file with the contents of any of the test suites available from the C3D web site or the sample files supplied with the two viewer applications.

> Many C3D applications may expect that the frame count will be stored as a 16-bit integer although the C3D format supports storing the frame count as either an integer or a floating-point value.

All early C3D files will have less than 32767 frames and most applications should open these files without any problems. Files created in the early 2000’s may have frame ranges from 32767 to 65535 frames and some applications may have problems opening these files. In recent years C3D files with more than 65535 frames have been appearing and manufacturers have invented various methods of storing the frame count that may not be understood by all applications. In addition the increased frame count may cause internal overflow errors in some applications that were written for the clinical environment where data collections are typically less than a couple of minutes.

The [Mokka](https://biomechanical-toolkit.github.io/mokka/) application (MOtion Kinetic and Kinematic Analyzer) is an unsupported, user written application, that can be downloaded from the c3d.org web site and displays the C3D file contents in a graphical environment which makes it easy to visualize and examine the 3D and analog data contained in the C3D file. The [Mokka](https://biomechanical-toolkit.github.io/mokka/) graphical interface makes C3D data visualization convenient but it does not provide a detailed breakdown of the C3D file contents and, as a user written application, it is unsupported and as a result it may report “errors” due to some misunderstandings about the details of the C3D file format, so any error messages displayed by [Mokka](https://biomechanical-toolkit.github.io/mokka/) may be a result of internal [Mokka](https://biomechanical-toolkit.github.io/mokka/) issues. For example when a C3D file does notcontain any force plate data and the FORCE_PLATFORM:USED parameter has been set 0 (conforming to the C3D format) [Mokka](https://biomechanical-toolkit.github.io/mokka/) may report that the force plate location parameters are missing even though the C3D file parameters have documented that there are no force plates. So the “error” that [Mokka](https://biomechanical-toolkit.github.io/mokka/) reports may be an internal coding error, not an actual C3D file error in some cases. As a result [Mokka](https://biomechanical-toolkit.github.io/mokka/) is mainly a convenient way to view the C3D file data and while the error logger reports may be helpful, they are not always accurate.

Since [Mokka](https://biomechanical-toolkit.github.io/mokka/) allows the user to save the C3D file after it has been opened it offers both the chance to “fix” an error or create a new error if the file is saved.

If you want to review the contents of the C3D file in detail then [EZC3D](https://github.com/pyomeca/ezc3d) and SHARP3D are a
good choice. They it will open most C3D file.

If you are still having problems opening a file, but the [EZC3D](https://github.com/pyomeca/ezc3d) or SHARP3D allows you to see the file contents, then the next step is to debug the file contents using the details described in this [C3D User Guide](https://www.c3d.org/docs/C3D_User_Guide.pdf) as a reference for the contents and structure of the C3D file.

The C3D file format is an efficient binary format that has existed for a very long time. As a result of the binary format, the peculiarities and many exceptions accumulated through time, writing data to the C3D file format is a little complex and it is not uncommon for new application programmers to fail to understand the format detail and capabilities. This can result in new applications creating C3D files that they can read but other applications are unable to open or open and display incorrect values. If you cannot get [Mokka](https://biomechanical-toolkit.github.io/mokka/), or other applications mentionned above to open the file and display the contents then you can be confident that it is either corrupt, or not a C3D file.

The next option is to use a binary file hex editor to examine the file at a binary level. The first 512 bytes of the file form the [C3D header](../../c3d-header.md) that defines the C3D file structure and is documented byte by byte in this user guide together with all the [parameter and group formats](../../parameters/c3d-parameter-section.md). As a result the C3D file can be examined with a binary file editor to verify the contents.

> The original author of the [C3D User Guide](https://www.c3d.org/docs/C3D_User_Guide.pdf) mentionned HxD as free hex editor that can open, display, and edit the contents of C3D files at a binary level. We personnally recommend [ImHex](https://imhex.werwolv.net/) and [Ghidra](https://github.com/NationalSecurityAgency/ghidra). They are both free and open source Hex editor with packed a lot of tools.

For example, a detailed examination of the C3D file header record shown above at a binary level enables us to verify that the parameters start in the second 512 byte block, and the file stored data from twenty-six 3D points, sixteen analog channels and contains 450 frames of raw data, recorded at fifty frames/second with four samples of analog data stored with each 3D point frame sample. While examining a C3D file byte by byte at a binary level with a hex editor can be time consuming, the documentation in this user guide allows you to verify, and even edit if necessary, individual parameters within the file at a binary level and verify the internal structure.
